# Artwork startup and memory

The decoded-image LRU is limited to 32 MiB and 70 entries, independently of the total number of games. It retains display-sized bitmaps for reuse and evicts older entries when either bound is reached. Current panels, short-lived transition layers, WPF/graphics resources and normal application data consume memory outside that LRU; 32 MiB is not a cap on the whole process. The disk artwork cache is separate and is not deleted by RAM eviction. Closing the process discards the RAM cache; the next start decodes the visible images from disk again.

Startup reads the cached library before background launcher refresh. Rebuilding custom-game entries from settings must restore their downloaded artwork references and saved manual overrides immediately. Otherwise correct cached covers can appear as placeholders until the scan finishes. Startup restoration checks cached references without decoding the entire library, respects current local/manual choices, and does not resurrect a cleared manual assignment from old library metadata. Normal background validation and downloading remain in place.

`StartupArtworkTests` covers downloaded/local/manual artwork on the initial render, cleared-image safety, reopening and a library with 1,500 unrelated emulator games. `OverlayTests` separately fills and evicts decoded images and checks the 32 MiB bound and reuse of frequently accessed covers. Run `StartupArtworkTests.exe <data-folder>` for an optional read-only profile using a temporary copy of the settings/library and their relative manual images. No API key is copied, no game is launched, and preview mode disables background downloads. Image files referenced by absolute paths are read in place; the installed executable and user data are not changed.
